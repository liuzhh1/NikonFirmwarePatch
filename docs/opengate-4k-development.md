# 4K Open Gate 开发记录

当前阶段：已下载并核对原厂固件，完成模式表检查和现有画幅组的源码构建基线。**尚未实现 4K Open Gate 录像，也没有可供上机的新增固件。**

## 第一阶段目标

| 项目 | 开发目标 |
|---|---|
| 格式 | 沿用 N-RAW / NEV |
| 有效尺寸 | 4128×2752，3:2 |
| 视角 | 保留全高 FX 构图；必须与照片参照比较 |
| 首批帧率 | 菜单 30p、25p、24p；保留各自实际有理数帧率 |
| 现有模式 | 保留 8.3K Open Gate 和原厂 16:9 模式 |
| 采样方式 | 尚未确定，不能宣称超采样、像素合并或跳行 |

4128×2752 是按现有 FX 宽度一半定义的有效区域，不是 UHD 3840×2160。编码尺寸、内部缓冲高度和传感器驱动编号必须分别核对，不能由这个比例直接推出。

## 已找到的入口

- `z8opengate/src/menu_repair_hooks.S` 的 `configuration_hook` 同时修改全分辨率和半分辨率几何；当前录像条件仍限定 size code 6（8.3K）。
- 同文件 `driver_hook` 的现有半分辨率分支使用 driver 14。它出现在当前取景相关链路中，不能作为 4K 录像驱动已经成立的证据。
- 当前生效的 `ui_hooks.S` 中，`half_size_hook` 使用有效高度 2752，`half_extent_hook` 涉及宽度 4140、内部高度 2756、extent 2760。这些数值属于不同阶段，不能全部替换成 2752。
- `d8_hooks.S` 的 `og_gate_wanted` 和底层 `require_selected_video` 仍检查 8.3K 身份。放宽其中一个条件会让状态判断不一致。
- `d10_hooks.S` 的回放识别只接受 8256×5504。缩略图、代理、AF 和反挤压也有相应尺寸条件。
- `patcher.py` / `imenu.py` 目前只增加三行 8.3K 选项；码率表和剩余时间表也只扩展这三个模式。

## 只读检查工具

工具不依赖编译器或 Capstone，不生成或修改固件。

```sh
# 仅记录源码入口与未解决事项。
python tools/inspect_opengate4k.py --source-only --output build/opengate4k/source.json

# 核对完整原厂 C3.11 的身份，再读取相关初始表。
python tools/inspect_opengate4k.py /path/to/Z_8_0311.bin --output build/opengate4k/stock.json

# 无固件输入的解析与负向回归。
python -B -m unittest discover -s tests -p test_opengate4k_probe.py
```

原厂输入必须满足 `resources/input.json` 的长度与 SHA-256；不接受仅解包的 MAIN、C3.12 或已修改文件。输出路径必须是新的 JSON 文件。错误输入不会创建输出目录。

工具提取 42 条配对码率记录、原厂 N-RAW 菜单映射和已知几何字段的初始值，帮助比较 4.1K 与 8.3K 路径。它不执行 CPU，也不能读取运行时寄存器或证明传感器行为。

## 原厂 C3.11 已核对的事实

2026-11-10 从 README 已列出的 Nikon 服务器直接取得完整输入。长度为 99,051,117 字节，SHA-256 为 `d67413c2ede6b9ce8887175f20700bd9fbad2a973a4820968c45503d15d80d96`；解析后的 EG SHA-256 为 `f85e0138e2f5e660ece8560de62e0d12cb795e0e14983e50f20b61dce906c46c`。输入和解包内容仅用于本地开发，不加入 Git。

主菜单的一条记录依次包含 `item, file_type, rate, size, variant, resource`。8.3K 的 `file_type` 与 `size` 恰好均为 6；4.1K 的 `file_type` 仍为 6，而 `size` 为 4。检查工具已用两张独立的 i 菜单品质表交叉核对全部 19 个 N-RAW 选项，并加入字段转置回归。

| 4.1K 普通录像 | 实际帧率 | 尺寸代码 | 主菜单行 / item | i 菜单行 | High / Normal 预算 |
|---|---|---|---|---|---|
| 30p | 30000/1001 | 4 | 60 / `0x30fa` | 9 | 898 / 468 Mbps |
| 25p | 25000/1000 | 4 | 61 / `0x30fb` | 10 | 758 / 398 Mbps |
| 24p | 24000/1001 | 4 | 62 / `0x30fc` | 11 | 728 / 378 Mbps |

这些是**原厂 16:9** 模式，编码尺寸为 4140×2330。表中的预算不是新 3:2 模式的码率，不能按高度比例直接视为已验证参数。

原厂初始化数据中，全分辨率读出高度为 4688、有效高度为 4644；半分辨率读出高度为 2344、有效高度为 2322。原补丁中的 2756、2752、2760 仍分别属于不同处理阶段，尚不能当成已核对的 4K Open Gate 录像描述。

对原厂驱动选择叶函数进行有界 AArch64 隔离执行，合成输入 `kind=5, readout=8, variant=3` 返回 driver 15，`kind=8, readout=8` 返回 driver 14。这只说明不同输入走不同分支；尚未证明某组输入可由实际 4.1K 拍摄状态到达，也不证明物理传感器输出。

- 安装项目固定的 Capstone 5.0.7。
- 使用本地 Zig 0.16.0 所带 Clang 21.1.0，将目标三元组对应为 `aarch64-freestanding-none` 并关闭 Zig 默认调试信息；没有修改仓库编译器或配方。
- 重新汇编 Open Gate 单元并执行原有链接修正，11,568 字节的机器码 SHA-256 为 `693269ed8db5066947132e1885bc3063aa070f815995b8a0f009e62c50fc246d`，与审阅配方相同，导出符号也相同。
- 从已核对原厂输入构建原有 `framing` 组，使用离线测试身份 `00.00.t0`；构建器内的独立校验返回通过。输出 SHA-256 为 `f925389edb38831bbda6fc2906de0dbef81589dcf46fc4294383b6f0f5e339d8`。这是现有画幅组基线，不是新增 4K Open Gate 固件。
- 新增检查工具的解析与负向测试扩展至 17 项；原有预编译路径测试为 8 项。

## 后续实现顺序与验收

1. 已完成输入身份、4.1K 菜单尺寸代码及独立 i 菜单映射核对；继续确认实际 4.1K 录像状态的 readout/plan 身份和前端资源选择。工具报告中菜单与码率表是分开的证据，不直接假定二者的索引一致。
2. 追踪 4.1K 录像实际使用的驱动和缓冲区；确认全高采样与 Bayer 排列、行步长、对齐和编码范围一致。
3. 同步加入独立菜单选项、i 菜单、取消回滚、菜单库和断电恢复；保持现有模式状态自洽。
4. 同步处理编码描述、裁切/尺寸元数据、四档 N-RAW 码率与剩余时间、代理、回放、AF 和反挤压。
5. 审阅新机器码、符号和保留区，再生成组合配方。保留原输入哈希及独立校验，不用绕过检查来接受新代码。
6. 进行有界执行和机身录制测试：同场照片确认上下视角、检查边缘 Bayer/坏行、完整解码首尾和长片段、核对代理与回放几何、退出模式和取消后正常关机。

当前未增加 `patch.py` 的新选项，未修改任何已审阅的编译单元或配方。本研究工具也不在原发布工具包的显式成员清单内；它随实验分支源码使用，后续功能验收后再决定发布包范围。
