# 4K Open Gate 开发记录

当前阶段：已完成原厂模式的运行时追踪，并新增 4K 前端 AArch64 原型和独立模拟器 MAIN 构建入口。**尚未实现 4K Open Gate 录像，也没有可供上机的新增固件。**

2026-11-10 补充：用户提供的 `03.11.p0` 四组功能全选自制固件已通过独立配方核验，并在现有 Z8 QEMU 模型中完成启动、菜单和返回合成取景测试（1083 项运行时断言通过）。已增加受完整包校验约束的复跑入口；详见 [自制固件测试记录](custom-firmware-smoke.md)。该结果是既有功能的运行基线，尚未验证新的 4K 录像路径。

## 第一阶段目标

| 项目 | 开发目标 |
|---|---|
| 格式 | 沿用 N-RAW / NEV |
| 有效尺寸 | 4128×2752，3:2 |
| 视角 | 保留全高 FX 构图；必须与照片参照比较 |
| 首批帧率 | 菜单 30p、25p、24p；保留各自实际有理数帧率 |
| 现有模式 | 保留 8.3K Open Gate 和原厂 16:9 模式 |
| 采样方式 | 尚未确定，不能宣称超采样、像素合并或跳行 |

4128×2752 是按现有 FX 宽度一半定义的有效区域，不是 UHD 3840×2160。编码尺寸、内部缓冲高度和传感器驱动编号必须分别核对，不能由这个比例直接推出。

## 已找到的入口

- `z8opengate/src/menu_repair_hooks.S` 的 `configuration_hook` 同时修改全分辨率和半分辨率几何；当前录像条件仍限定 size code 6（8.3K）。
- 同文件 `driver_hook` 的现有半分辨率分支使用 driver 14。它出现在当前取景相关链路中，不能作为 4K 录像驱动已经成立的证据。
- 当前生效的 `ui_hooks.S` 中，`half_size_hook` 使用有效高度 2752，`half_extent_hook` 涉及宽度 4140、内部高度 2756、extent 2760。这些数值属于不同阶段，不能全部替换成 2752。
- `d8_hooks.S` 的 `og_gate_wanted` 和底层 `require_selected_video` 仍检查 8.3K 身份。放宽其中一个条件会让状态判断不一致。
- `d10_hooks.S` 的回放识别只接受 8256×5504。缩略图、代理、AF 和反挤压也有相应尺寸条件。
- `patcher.py` / `imenu.py` 目前只增加三行 8.3K 选项；码率表和剩余时间表也只扩展这三个模式。

## 只读检查工具

工具不依赖编译器或 Capstone，不生成或修改固件。

```sh
# 仅记录源码入口与未解决事项。
python tools/inspect_opengate4k.py --source-only --output build/opengate4k/source.json

# 核对完整原厂 C3.11 的身份，再读取相关初始表。
python tools/inspect_opengate4k.py /path/to/Z_8_0311.bin --output build/opengate4k/stock.json

# 无固件输入的解析与负向回归。
python -B -m unittest discover -s tests -p test_opengate4k_probe.py
```

原厂输入必须满足 `resources/input.json` 的长度与 SHA-256；不接受仅解包的 MAIN、C3.12 或已修改文件。输出路径必须是新的 JSON 文件。错误输入不会创建输出目录。

工具提取 42 条配对码率记录、原厂 N-RAW 菜单映射和已知几何字段的初始值，帮助比较 4.1K 与 8.3K 路径。它不执行 CPU，也不能读取运行时寄存器或证明传感器行为。

## 原厂 C3.11 已核对的事实

2026-11-10 从 README 已列出的 Nikon 服务器直接取得完整输入。长度为 99,051,117 字节，SHA-256 为 `d67413c2ede6b9ce8887175f20700bd9fbad2a973a4820968c45503d15d80d96`；解析后的 EG SHA-256 为 `f85e0138e2f5e660ece8560de62e0d12cb795e0e14983e50f20b61dce906c46c`。输入和解包内容仅用于本地开发，不加入 Git。

主菜单的一条记录依次包含 `item, file_type, rate, size, variant, resource`。8.3K 的 `file_type` 与 `size` 恰好均为 6；4.1K 的 `file_type` 仍为 6，而 `size` 为 4。检查工具已用两张独立的 i 菜单品质表交叉核对全部 19 个 N-RAW 选项，并加入字段转置回归。

| 4.1K 普通录像 | 实际帧率 | 尺寸代码 | 主菜单行 / item | i 菜单行 | High / Normal 预算 |
|---|---|---|---|---|---|
| 30p | 30000/1001 | 4 | 60 / `0x30fa` | 9 | 898 / 468 Mbps |
| 25p | 25000/1000 | 4 | 61 / `0x30fb` | 10 | 758 / 398 Mbps |
| 24p | 24000/1001 | 4 | 62 / `0x30fc` | 11 | 728 / 378 Mbps |

这些是**原厂 16:9** 模式，编码尺寸为 4140×2330。表中的预算不是新 3:2 模式的码率，不能按高度比例直接视为已验证参数。

原厂初始化数据中，全分辨率读出高度为 4688、有效高度为 4644；半分辨率读出高度为 2344、有效高度为 2322。原补丁中的 2756、2752、2760 仍分别属于不同处理阶段，尚不能当成已核对的 4K Open Gate 录像描述。

对原厂驱动选择叶函数进行有界 AArch64 隔离执行，合成输入 `kind=5, readout=8, variant=3` 返回 driver 15，`kind=8, readout=8` 返回 driver 14。这只说明不同输入走不同分支；实际原生设置链路的观测见下文，物理传感器输出仍未验证。

## 后续实现顺序与验收

1. 已完成输入身份、4.1K 菜单尺寸代码及独立 i 菜单映射核对，并捕获原生设置链路的 readout/plan 身份。工具报告中菜单与码率表是分开的证据，不直接假定二者的索引一致。
2. 追踪 4.1K 录像实际使用的驱动和缓冲区；确认全高采样与 Bayer 排列、行步长、对齐和编码范围一致。
3. 同步加入独立菜单选项、i 菜单、取消回滚、菜单库和断电恢复；保持现有模式状态自洽。
4. 同步处理编码描述、裁切/尺寸元数据、四档 N-RAW 码率与剩余时间、代理、回放、AF 和反挤压。
5. 审阅新机器码、符号和保留区，再生成组合配方。保留原输入哈希及独立校验，不用绕过检查来接受新代码。
6. 进行有界执行和机身录制测试：同场照片确认上下视角、检查边缘 Bayer/坏行、完整解码首尾和长片段、核对代理与回放几何、退出模式和取消后正常关机。

生产入口 `patch.py` 未增加 4K 选项，既有审阅编译单元和组合配方未修改。实验入口及限制见 [4K 前端原型](../z8opengate4k/README.md)。本研究工具也不在原发布工具包的显式成员清单内；它随实验分支源码使用，后续功能验收后再决定发布包范围。

## 已捕获的 4.1K N-RAW 运行时配置

原厂 30p 的真实原生设置链路已到达：snapshot kind=1、nominal readout=4、actual readout=8、size=4、rate=4、request=4；驱动输入 kind=5/readout=8/variant=2，返回 driver15；前端 plan=11，输出 4140×2344，活动区 4128×2322。代码外的合成硬件输入仍属于模拟器配置。精简证据见 [运行记录](data/opengate4k-stock-runtime.json)。

这解释了两个原先未确认的缺口：既有半分辨率计划只处理类型10；既有驱动钩子位于 variant3 路径，而原厂30p到达的是 variant2。新原型分别增加 plan11 和共享驱动入口处理，并在隔离执行中验证 variant2/3 及非目标回退。

现有 QEMU 在原厂路径到达 `PC 0x40C26810`、向 `0x15432004` 写入 `0x101` 时停止。该设备模型只承认有限的特定视频配置，本轮没有改写硬件模型或跳过停止条件。运行时设置到达不代表已成功录制，编码和物理读出仍需另外验证。

## 4K 前端原型实际到达的范围

原型主菜单包含三个 4K LAB 行、三个既有 8.3K 开放门行和 80 个原厂行；36 种语言的原厂偏移表及 88 条既有新增文本均保留。新增代码单独放置，不改既有 D10 代码地址。46 项测试通过，包括真实机器码执行及完整基线的构建集成检查。

原生选择 LAB 30p 并切换视频模式后，已捕获 size4/rate4、actual readout8、实验 driver14，以及写入后的有效区域 4128×2752、物理几何 4140×2756、逻辑范围 4140×2760；代理字段仍为 1920×1080。详见 [原型运行记录](data/opengate4k-lab-runtime.json)。

补查原生 UART 后，原始故障定位为 CAPTG 在 `PC 0x41170D84` 的读取地址翻译异常（ESR=`0x96000005`，FAR=`0x2A156B2806`，LR=`0x411643B0`）。此前记录的 `PC 0x40C07C24` 读取 `0x15080014`，属于异常之后的寄存器转储，是后续停止点。QEMU 源码的 `Z8_RAMDMP_LOAD_PC` 及 `docs/native-mcu.md` 已说明这种区分。

`0x41170CE0` 的原生函数将描述符映射到外部 ROM 选择表索引；本次异常寄存器 X8 为15，而运行配置只提供 Movie selector10 和16。选择字节为零会经减一、移位产生越界记录地址，因此缺少 selector15/记录输入是具体候选原因，仍需直接观察选择字节和基址来确认。driver14 目前也只是未完成物理验证的候选，不应把转储停止点当作它不适用的证据。最终视频快照之后的 plan11、编码配置及帧输出仍无运行时证明，25p/24p 尚未逐档追踪。i 菜单、取消回滚、元数据、码率预算及文件验证继续按上述顺序推进。

## 既有 8.3K Open Gate 的实现区别

原项目的 `configuration_hook` 保留原生 readout4 / plan12 身份，将 RAW 流描述、前端和路由的全高同步为5520，有效高度同步为5504。`driver_hook` 对这条全分辨率路径把默认视频驱动7切换为原厂全高连续驱动2；同一个钩子的 readout8 分支返回14，配合2756/2752几何服务于半分辨率取景。后者不是既有8.3K主录像编码路径。

`inner_hook`、`record_hook`、`nrmt_hook`、`crop_hook` 和 NCTG 钩子同步编码尺寸8268×5512、有效尺寸8256×5504及裁切身份；菜单、码率、取景/AF、取消恢复和回放另有配套实现。新4K实验不能仅将取景驱动14和2752高度迁入录像，必须为实际 readout8 / plan11 的记录链路分别验证。
