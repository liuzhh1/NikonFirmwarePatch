## 已找到的入口

- `z8opengate/src/menu_repair_hooks.S` 的 `configuration_hook` 同时修改全分辨率和半分辨率几何；当前录像条件仍限定 size code 6（8.3K）。
- 同文件 `driver_hook` 的现有半分辨率分支使用 driver 14。它出现在当前取景相关链路中，不能作为 4K 录像驱动已经成立的证据。
- 当前生效的 `ui_hooks.S` 中，`half_size_hook` 使用有效高度 2752，`half_extent_hook` 涉及宽度 4140、内部高度 2756、extent 2760。这些数值属于不同阶段，不能全部替换成 2752。
- `d8_hooks.S` 的 `og_gate_wanted` 和底层 `require_selected_video` 仍检查 8.3K 身份。放宽其中一个条件会让状态判断不一致。
- `d10_hooks.S` 的回放识别只接受 8256×5504。缩略图、代理、AF 和反挤压也有相应尺寸条件。
- `patcher.py` / `imenu.py` 目前只增加三行 8.3K 选项；码率表和剩余时间表也只扩展这三个模式。

## 只读检查工具

工具不依赖编译器或 Capstone，不生成或修改固件。

```sh
# 仅记录源码入口与未解决事项。
python tools/inspect_opengate4k.py --source-only --output build/opengate4k/source.json

# 核对完整原厂 C3.11 的身份，再读取相关初始表。
python tools/inspect_opengate4k.py /path/to/Z_8_0311.bin --output build/opengate4k/stock.json

# 无固件输入的解析与负向回归。
python -B -m unittest discover -s tests -p test_opengate4k_probe.py
```

原厂输入必须满足 `resources/input.json` 的长度与 SHA-256；不接受仅解包的 MAIN、C3.12 或已修改文件。输出路径必须是新的 JSON 文件。错误输入不会创建输出目录。

工具提取 42 条配对码率记录、原厂 N-RAW 菜单映射和已知几何字段的初始值，帮助比较 4.1K 与 8.3K 路径。它不执行 CPU，也不能读取运行时寄存器或证明传感器行为。

## 已捕获的 4.1K N-RAW 运行时配置

原厂 30p 的真实原生设置链路已到达：snapshot kind=1、nominal readout=4、actual readout=8、size=4、rate=4、request=4；驱动输入 kind=5/readout=8/variant=2，返回 driver15；前端 plan=11，输出 4140×2344，活动区 4128×2322。代码外的合成硬件输入仍属于模拟器配置。精简证据见 [运行记录](data/opengate4k-stock-runtime.json)。

这解释了两个原先未确认的缺口：既有半分辨率计划只处理类型10；既有驱动钩子位于 variant3 路径，而原厂30p到达的是 variant2。新原型分别增加 plan11 和共享驱动入口处理，并在隔离执行中验证 variant2/3 及非目标回退。

现有 QEMU 在原厂路径到达 `PC 0x40C26810`、向 `0x15432004` 写入 `0x101` 时停止。该设备模型只承认有限的特定视频配置，本轮没有改写硬件模型或跳过停止条件。运行时设置到达不代表已成功录制，编码和物理读出仍需另外验证。

## 4K 前端原型实际到达的范围

原型主菜单包含三个 4K LAB 行、三个既有 8.3K 开放门行和 80 个原厂行；36 种语言的原厂偏移表及 88 条既有新增文本均保留。新增代码单独放置，不改既有 D10 代码地址。初版46项测试通过；增加本轮诊断回归后为51项，包括真实机器码执行及完整基线的构建集成检查。

原生选择 LAB 30p 并切换视频模式后，已捕获 size4/rate4、actual readout8、实验 driver14，以及写入后的有效区域 4128×2752、物理几何 4140×2756、逻辑范围 4140×2760；代理字段仍为 1920×1080。详见 [原型运行记录](data/opengate4k-lab-runtime.json)。

补查原生 UART 后，原始故障定位为 CAPTG 在 `PC 0x41170D84` 的读取地址翻译异常（ESR=`0x96000005`，FAR=`0x2A156B2806`，LR=`0x411643B0`）。此前记录的 `PC 0x40C07C24` 读取 `0x15080014`，属于异常之后的寄存器转储，是后续停止点。QEMU 源码的 `Z8_RAMDMP_LOAD_PC` 及 `docs/native-mcu.md` 已说明这种区分。

`0x41170CE0` 的原生函数将描述符映射到外部 ROM 选择表索引；该次异常寄存器 X8 为15，而当时只提供 Movie selector10 和16。选择字节为零会经减一、移位产生越界记录地址；这一候选原因及 plan11 配置已在下文的后续对照中确认。driver14 仍是未完成物理验证的候选，编码和帧输出尚无运行时证明，25p/24p 尚未逐档追踪。i 菜单、取消回滚、元数据、码率预算及文件验证继续按上述顺序推进。

## selector15 的 A/B 确认与新的运行边界

继续开发时已完成上述直接观测。同一 MAIN、QEMU、合成 RAW 和按键列表，使用两份独立虚拟卡：A 读到 selector15=0，在减一后得到越界记录基址 `0x2A155D78A0`，参数读取地址与原 UART 的 FAR 相同；B 仅增加外部 ROM `0x47F5AF4F=1`，记录基址回到 `0xA155D78C0`，参数可读，未再输出原生异常。该对照确认了本次异常的合成输入缺口，没有恢复工厂校准或证明驱动14适用于物理录像。

追踪入口新增明确开关 `--experimental-movie-selector15`、三个 ROM 读断点、视频快照之后的重新布点，以及自动提取首个原生 UART 异常。最终视频快照之后已实际捕获 plan11 和前端4140×2756；编码候选仍未到达。新增五项原始异常回归后，全套51项测试通过。

B 随后在 `PC 0x40C26810` 向 `0x15432004` 写入 `0x101` 时被模型停止。比较 header 与 supplier 两块配置，所有字段与原厂 N-RAW 对照相同；source1518 的配置也同为零。模型当前只接受 supplier/source 参数完整的 video START，下一步需要追踪和验证 N-RAW 的 header 与 supplier 启动顺序。没有修改模型、跳过访问或产生模拟编码完成事件，仍未开始录像。精简的读值、地址、原异常和下一边界见 [A/B 证据](data/opengate4k-selector-ab.json)。

## 既有 8.3K Open Gate 的实现区别

原项目的 `configuration_hook` 保留原生 readout4 / plan12 身份，将 RAW 流描述、前端和路由的全高同步为5520，有效高度同步为5504。`driver_hook` 对这条全分辨率路径把默认视频驱动7切换为原厂全高连续驱动2；同一个钩子的 readout8 分支返回14，配合2756/2752几何服务于半分辨率取景。后者不是既有8.3K主录像编码路径。

`inner_hook`、`record_hook`、`nrmt_hook`、`crop_hook` 和 NCTG 钩子同步编码尺寸8268×5512、有效尺寸8256×5504及裁切身份；菜单、码率、取景/AF、取消恢复和回放另有配套实现。新4K实验不能仅将取景驱动14和2752高度迁入录像，必须为实际 readout8 / plan11 的记录链路分别验证。

## 2026-11-12：header 控制已继续，视频数据尚未启动

## 原始 EX 的 N-RAW/Record 与零视频帧的直接原因

原厂MAIN/EX在修正调度的模型中已原生选择N-RAW4.1K30p并切入Movie，再发出一次Record按下/释放。EX报告字节9在13个样本中为1，MAIN缓存SW1掩码0x2000同时置位；原生交换1431/1412帧、坏帧0。337项串行/运行检查通过，正常退出，无UART原始异常或未建模访问。

前一快照58.027虚拟秒的source2控制为0、主输入active为6；最终75.911虚拟秒分别为1和65375，ISP1有三次真实START日志。这里的0x218为配置项，实际START寄存器是实例偏移0x8，不能仅凭0x218为0断言ISP1未启动。两份快照尚不能单独证明变化由Record触发；观察器新增有界控制状态变化历史供后续确定时序。

当前零帧有明确的模型阻塞：`og4k_header_poll`要求`engine1543_video_ready`，后者只检查source0，而此处source0为空，等待始终没有释放。实际N-RAW走source2/ISP1；shared profile也未启用既有secondary ISP/sensor模型，后者要求的0x218=1与最终原生布局0不同。这些数据路径条件尚未适配。`raw_pipeline_video_frames`在实际RAW/ISP图像缓冲写出后增加，并不是TICO/H264编码帧数。因此零帧描述模拟器的传输状态，不能据此判断实体机4K Open Gate的可行性。

原厂计算行步长为7264字节，因此最低RAW栅格跨度从17,026,816增为20,019,584字节，差2,992,768字节。这不是总RAM预算或实际池容量，也不是压缩NEV帧大小；池可能已预留更大空间。逻辑2760行与物理2756行保持分开。尚未观察RAW缓冲对应单槽大小、头部/对齐或分配与配置安装的顺序，不能判断内存是否充足。

静态追踪补齐此前BL索引未覆盖的尾跳入口：ExRecord的0x40F856B4调用0x40723778，后者尾跳0x407218E4，复制0x48字节请求到0xA046130B8并通知任务。消息+0x38保存的请求指针来自全局0xA03BC2EC0+0x38对象的+8载荷。录制任务随后读取该指针内容；实际对象生产者、值和时序仍未执行验收，不能认定真实录制已选择测试中的请求种类1。

新增6项机器码执行、2项输入拒绝和1项窗口核对，完整项目171项通过、无跳过，109项AArch64执行、19项完整输入构建。覆盖配置安装前后、三个低帧率描述、有效关闭/不支持模式、无效快照保持原行为，以及4K→原8K与新鲜8K描述一致；10段原厂窗口与自制基线相同。未修改任何固件字节，MAIN仍为f80ee74d…；无新的完整QEMU、分配器或实机录像结果。数值、输入和执行范围见[缓冲核对记录](data/opengate4k-native-buffer-audit.json)。
